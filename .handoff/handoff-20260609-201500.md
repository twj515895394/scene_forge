### 1.2 WebSocket + Claude 桥接

- `claude --print` 非交互模式，每次消息 spawn 独立进程
- `--session-id <uuid>` / `--resume <uuid>` 实现多连接会话隔离
- 首次消息自动注入项目上下文（AGENTS.md 指引 + 管线描述 + 项目状态）
- Claude CWD = scene_forge 根目录，用相对路径访问一切
- 取消操作为 SIGINT 仅中断当前操作
- `+ 新会话` 按钮生成新 UUID，重置上下文

### 1.3 前端重构

- 引入 shadcn/ui + Tailwind CSS 作为标准 UI 库
- 原 2000+ 行 App.css 拆分为 6 个组件级 CSS 文件
- 统一使用 Variant B（Swiss Neo-Geek Grid）为唯一 UI 主题
- Lobby.tsx 用 shadcn 组件重写（Card/Button/Input/Textarea/Badge/Alert/ScrollArea）
- 所有滚动区域使用 ScrollArea 替代原生滚动条
- 历史会话面板（ChatHistory.tsx）——从 Claude 本地文件加载
- 聊天记录不再依赖 localStorage，改为直接从 Claude 会话恢复

### 1.4 工作流正确化（最后一次改动）

- `activeStage` 不再手动选择，自动从 PROJECT_STATE.json 的 `current_stage` 或首个未完成阶段读取
- 时间轴侧栏改为只读状态展示
- 移除旧 CLI 宏按钮（START/VALIDATE/COMPLETE）
- 操作栏改为显示当前阶段状态 + "通过对话驱动 Claude 推进管线" 提示
- Claude 首次消息注入上下文：管线段落、当前状态、AGENTS.md 指向

## 2. 关键待测试项

### 2.1 阶段流转端到端（高风险）

当前阶段流转**依赖 Claude 自主读写 PROJECT_STATE.json**，但从代码层面：

- StateMachine (`packages/engine/src/state_machine.ts`) 实现完整：`ready → in_progress → validated → completed`
- CLI (`packages/engine/src/cli.ts`) 有 `start/validate/complete` 命令，但我们**不再通过 CLI 调用**，而是靠 Claude 直接操作文件
- **需要验证**：Claude 是否真的会按 SOP 读完 AGENTS.md → PROJECT_STATE.json → PROJECT_BOARD.md 后正确推进阶段？

**测试方法**：
1. 新建项目，确认 PROJECT_STATE.json 初始状态 7 阶段全为 `ready`
2. 在聊天框输入"帮我选题"
3. 观察 Claude 是否：
   - 先读 `./AGENTS.md`
   - 再读 `projects/<slug>/PROJECT_STATE.json`
   - 再读 `projects/<slug>/PROJECT_BOARD.md`
   - 输出 topic_gate 阶段产物
   - 更新 PROJECT_STATE.json 将 topic_gate 标记为 completed
   - 解锁 script 阶段
4. 检查前端时间轴是否实时更新（FileWatcher → WebSocket → React state）

### 2.2 输出协议对齐

引擎层定义了产物规范：
- Artifact Manifest (`artifacts.manifest.yaml`)：记录产物 id/stage/kind/path
- Final 产物写入 `outputs/`，草稿写入 `details/<stage>/`
- Markdown 产物需带 YAML frontmatter

**需要验证**：Claude 生成的产物是否符合这些协议？
- Claude 是否知道要写 `artifacts.manifest.yaml`？
- Claude 是否把 final 写入 `outputs/` 而非 `details/`？
- 生成的 Markdown 是否有正确的 frontmatter？

### 2.3 上下阶段衔接

- `STAGE_DEPENDENCIES` 定义在 `state_machine.ts`：`script` 依赖 `topic_gate`，`performance` 依赖 `script`...
- Claude 的上下文提示包含了 "严格按阶段依赖顺序推进"，但**没有明确列出依赖关系**
- **需要验证**：Claude 在开始 script 前是否会检查 topic_gate 是否 completed？

### 2.4 前端状态同步

- FileWatcher 监听 `outputs/`、`details/`、`PROJECT_STATE.json`
- 文件变化通过 WebSocket `workspace_update` 事件推送
- 前端收到后更新 `projectState`，右侧预览区自动刷新
- **需要验证**：
  - Claude 写产物后，右侧预览是否在 500ms 内刷新？
  - 时间轴状态灯是否实时更新？
  - 多标签/多用户场景下状态是否会串？

### 2.5 多项目隔离

- 每个 WebSocket 连接有独立 sessionId
- 项目切换会重新连接 WebSocket
- **需要验证**：切换项目后，聊天记录和会话是否正确隔离？

## 3. 已知架构风险

### 3.1 Claude 不一定执行状态机逻辑

当前设计中，Claude 是通过自然语言提示 "引导" 去更新 PROJECT_STATE.json 的。**没有任何硬约束保证 Claude 会正确执行状态推进**。如果 Claude 跳过某个阶段直接写产物，系统不会拦截。

**可能的加固方案**（后续）：
- 在 Claude 的上下文中加入更严格的约束提示
- 或者在 WebSocket 层做拦截：监控 Claude 的文件写入，如果写入下游阶段产物但上游未完成就告警
- 或者保留 CLI 接口作为 "状态机闸门"，让 Claude 调 CLI 而不是直接写文件

### 3.2 产物协议依赖 Claude 自觉遵守

`artifacts.manifest.yaml` 的更新、frontmatter 的规范性等，目前全凭 Claude 在上下文中被告知的规则。没有程序化校验。

**engine 层已有的 Validator（Issue #3）可以在这里接入**——在 Claude 声称 "完成" 某阶段时，自动跑 `scene-forge validate` 校验产物。
