# Creative Story Planner

SceneForge 文本创作主链第 01 阶段。

本 Skill 解决一个核心问题：**到底要拍什么故事。**

它合并并吸收旧版 `scene-topic-gate`、`scene-reference-decider`、`scene-story-development` 的有效能力，但不再把它们拆成三个画布节点。

执行期通用约束遵循仓库根 `AGENTS.md`。本 Skill 只产出文本型创作资源，不声称已经生成任何图片、故事板图、音频或视频。

## 1. 何时使用

以下情况使用本 Skill：

- 用户只有一句创意、题材、主题或短视频想法，需要发展成可制作故事。
- 用户提供已有影视桥段、小说片段、剧本片段、截图、视频解析摘要或其他参考材料，希望做改编或再创作。
- 用户已经明确选择某个改写方向，需要把它发展成稳定故事骨架。
- 用户希望保留原剧情，只做结构化整理、风格化转译或时长压缩。
- 无限画布中的上游节点向本节点传入 `SOURCE_DOCUMENT`、自由文本或等价文本资料。

如果用户已经提供完整且确认过的 `01_CREATIVE_STORY.md`，不要重复执行；应直接交给下游 `production-designer` 或按用户要求局部修订。

## 2. 输入

至少需要以下任一输入：

- 用户自然语言创意；
- 已有故事、剧情梗概、剧本或小说片段；
- source intake 的文本化结果；
- 上游统一文档；
- 用户指定的题材、风格、时长、受众或改编方向。

可选输入：

- `script_mode`: `original | rewrite_adaptation | preserve_original`
- 目标总时长；
- 单段视频生成时长或分段偏好；
- `style_family`；
- `director_style_id`；
- 明确要求保留或避免的元素；
- 已选 adaptation idea；
- 参考作品、人物、时代、地点、题材限制。

不要因为可选字段缺失就无条件阻塞。能够从用户目标合理推断时先形成推荐方案；只有会显著改变故事方向的关键分歧才需要用户确认。

## 3. 输入读取边界

默认只读取：

1. 当前用户输入；
2. 当前节点收到的上游文档；
3. 当前项目中被显式引用的 source intake 文本；
4. 用户明确指定的参考资料；
5. 本 Skill 的 `references/output-contract.md` 与 `references/review-checklist.md`。

不得为了找灵感扫描其他项目、历史项目输出或整个 `docs/`。

如果输入来自视频/source intake，优先消费已经整理好的摘要、优先级图、改写方向和 handoff，不重新深读完整源材料，除非当前故事判断确实缺少必要信息。

## 4. 单一输出原则

本阶段只能产出 **一个权威阶段文档**：

```text
01_CREATIVE_STORY.md
```

禁止把以下内容拆成额外正式输出文件：

- topic 评分；
- reference boundary；
- story bible；
- Story Beats；
- risk review；
- adaptation decision；
- handoff。

这些都必须作为 `01_CREATIVE_STORY.md` 内的章节存在。

内部分析、草稿、评分过程和 review 过程不作为正式输出。

详细文档结构见：

```text
references/output-contract.md
```

## 5. 核心职责

本 Skill 必须完成以下工作。

### 5.1 理解创作目标

识别：

- 项目类型；
- 核心题材；
- 用户真正想看的冲突或情绪；
- 目标受众；
- 目标时长；
- 输出用途；
- 原创还是改编。

不要把“题材评分”本身当最终目的。评分只是一种内部决策辅助。

### 5.2 确定创作模式

必须明确以下一种模式：

```text
original
rewrite_adaptation
preserve_original
```

规则：

- `original`：用户从零创作，不强行引入参考作品边界。
- `rewrite_adaptation`：继承参考材料的抽象故事功能，但围绕用户已确认的改写方向重新组织人物、场景、关系或表达。
- `preserve_original`：保留原剧情或原桥段主结构，仅做标准化、节奏整理、视觉化转译和必要压缩。

如果用户已经明确选择模式，不得擅自改成另一种。

### 5.3 建立参考边界

仅当存在参考源时建立：

- `must_keep`
- `should_keep`
- `allowed_to_rewrite`
- `must_avoid`

参考边界服务创作，不应成为独立节点。

允许继承：

- 抽象冲突结构；
- 动作链；
- 情绪转折；
- 角色功能；
- 可泛化镜头功能；
- 用户明确要求保留的经典元素。

避免无必要照搬：

- 平台水印；
- 字幕版式；
- 品牌元素；
- 强绑定具体演员身份的视觉特征；
- 用户要求规避的具体表达。

### 5.4 确定故事核心

至少明确：

- Logline；
- Premise；
- 核心冲突；
- 情绪目标；
- 故事的起点、升级、高潮和结局；
- 观众最终应该获得什么感受或 payoff。

### 5.5 定义角色功能

这里只定义叙事功能，不进行完整视觉设计。

每个重要角色至少包含：

- 稳定 ID，例如 `CHAR_001`；
- 角色功能；
- 当前目标；
- 阻力或弱点；
- 与其他角色关系；
- 弧光或本片变化；
- 是否为主视角角色。

不要在本阶段详细规定服装纹理、发型细节、材质、镜头 Prompt 等视觉制作内容；这些属于 Stage 02。

### 5.6 设计 Story Beats

默认 4–8 个 Beats；超短内容可以更少，长内容可以更多，但每个 Beat 必须承担明确叙事功能。

每个 Beat 使用稳定 ID：

```text
BEAT_001
BEAT_002
...
```

每个 Beat 至少描述：

- 发生什么；
- 谁推动；
- 冲突如何变化；
- 情绪如何变化；
- 这个 Beat 为什么必须存在；
- 预计时长或时长权重。

### 5.7 建立风格与时长方向

输出适合下游继承的创作级方向，而不是图片 Prompt。

至少包含：

- `style_family` 或推荐候选；
- 视觉/叙事关键词；
- 节奏倾向；
- 目标总时长；
- 如已知，单段生成时长与分段策略。

## 6. 执行流程

严格按以下顺序思考与产出：

```text
理解输入
→ 判断 original / rewrite / preserve
→ 建立参考边界（如需要）
→ 确定核心故事与主题
→ 定义角色功能
→ 设计 Story Beats
→ 校准目标时长与节奏
→ 确定风格方向
→ 运行内部 review
→ 输出 01_CREATIVE_STORY.md
```

不要先写完整剧本，再倒推出 Story Beats。

## 7. 稳定 ID 规则

本阶段首次创建以下实体时必须使用稳定 ID：

- `CHAR_###`
- `BEAT_###`
- 如故事已明确关键地点，可提前创建 `SCENE_###`，但只描述叙事功能，不做完整视觉设定。
- 如关键道具承担剧情功能，可创建 `PROP_###`。

后续阶段必须继承这些 ID，不应无故重新编号。

## 8. 内部 Review

正式输出前必须按 `references/review-checklist.md` 自检。

Review 只用于修正：

- 逻辑缺口；
- 自相矛盾；
- Beat 功能重复；
- 时长明显失衡；
- 参考边界冲突；
- 角色功能缺失；
- 下游无法消费的模糊描述。

不得在 review 阶段悄悄改变用户已确认的题材、结局、改写方向或风格核心。

## 9. 下游交接

`01_CREATIVE_STORY.md` 必须让 `production-designer` 和 `script-director` 能直接消费。

文档末尾必须有 `Downstream Handoff`，至少明确：

- 已锁定的创作模式；
- 核心角色 IDs；
- Story Beat IDs；
- 必须保留/避免的内容；
- 下游 Stage 02 需要重点视觉化的角色、场景、道具；
- 下游 Stage 03 不得改变的故事事实；
- 仍未决但不阻塞的开放项。

## 10. 完成定义

只有同时满足以下条件才算完成：

1. 创作模式明确；
2. 故事核心明确；
3. 角色功能完整；
4. Story Beats 可执行；
5. 时长与节奏基本合理；
6. 如有参考源，参考边界明确；
7. 稳定 ID 已建立；
8. 文档经过内部 review；
9. 正式输出只有 `01_CREATIVE_STORY.md` 一个权威文档；
10. 下游无需重新猜测故事方向即可开始工作。
